# Playbook: mod

**For:**

- **Members:** any mod work. They can create branches.
- **Contributors:** changes to existing mods, by fork. A new mod starts with an issue.

**Asks like:**

- "Make a mod that installs ffmpeg into jellyfin."
- "Fix the code-server python mod."
- "Which mods exist for sonarr?"

**Output:** a PR to the mod's branch, or an issue asking for a new branch.

## How mods work

Mods are small images (`FROM scratch`) that LinuxServer containers apply at start-up through `DOCKER_MODS=`.
The rules:

- Each mod is one branch of `docker-mods`, named `<target>-<name>`. The target is an image name, or
  `universal` for any image.
- The branch carries `mod.yml`, a `Dockerfile` and `root/`. Its `README.md`, `AGENTS.md` and `build.yml` are
  generated by `builder render-mod` and committed with the change.
- `mod.yml` `images` lists the other images it suits.
- Read `repos/docker-mods/README.md` (how to write one) and its `AGENTS.md` (rules).

Existing mods: `curl -fsS https://linuxserver-playground.github.io/hub/api/v1/mods.json | jq -r '.data.mods[] | "\(.branch): \(.summary)"'`.

## Steps: change an existing mod

1. **Get it:** `./harness get docker-mods` (master only). Then
   `git -C repos/docker-mods fetch origin <branch>:<branch>` and
   `git -C repos/docker-mods worktree add ../docker-mods-<branch> <branch>`. The worktree lives at
   `repos/docker-mods-<branch>`.
2. **Contributors:** run `./harness fork docker-mods` first, and push the topic branch to the fork.
3. **Edit** `Dockerfile`, `root/` and `mod.yml` only. Then regenerate:
   `./harness render docker-mods-<branch> --in-place` (on mod branches, the generated files are committed
   with the change).
4. **Validate:** `./harness validate docker-mods-<branch>`. That runs `render-mod --check`,
   `tools/check-branch.sh` and `tools/test-mod.sh`. Success looks like
   `[mod-init] <name> applied to container`, then the mod's own lines, then `[ls.io-init] done.`
5. **Commit** with the title `<target>: <name> <short description>` (the mods convention). Push a topic
   branch.
6. **Draft the PR** against the mod's branch, never `master`: `./harness draft pr docker-mods <branch>`. Fix
   the title to the mods convention.

## Steps: a new mod

- **Members:**
  1. Create the branch from `template`:
     `git -C repos/docker-mods fetch origin template && git -C repos/docker-mods push origin origin/template:refs/heads/<target>-<name>`.
     This is a brand-new branch, so the guard hook lets it through.
  2. Then work on a topic branch off it, as above. The PR targets `<target>-<name>`.
  3. Follow `repos/docker-mods/README.md` "Submitting a mod" for the template's renames and permissions.
- **Contributors:**
  1. Build it in a fork from `template`, and validate it locally.
  2. Draft an issue on `docker-mods`, using `./harness draft issue docker-mods`. Include:
     - the proposed `<target>-<name>`;
     - what it installs, and for which images;
     - the `mod.yml`;
     - the test output.
  3. Once a member creates the branch, open the PR against it.

Mod PRs get less checking in CI than image PRs: no schema validation and no report comment. Your local
validation is what the reviewer sees, so paste it.
